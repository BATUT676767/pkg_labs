# Отчёт по лабораторной работе №2

**Тема:** чтение информации из графических файлов.

## 1. Цель и назначение приложения

Цель работы — изучить структуру растровых графических файлов и получить их характеристики непосредственным чтением заголовков, маркеров, чанков и тегов. Реализовано браузерное приложение на HTML, CSS и JavaScript.

Основные выводимые данные: имя, фактический формат, размеры в пикселях, разрешение по двум осям, глубина цвета, способ сжатия и результат проверки структуры. Дополнительно показываются размер файла, прочитанный объём, сведения о палитре, параметры формата и причина ошибки.

Сторонние библиотеки получения метаданных в приложении отсутствуют. Используются стандартные `File`, `Blob.slice()`, `ArrayBuffer`, `Uint8Array`, `DataView` и `Web Worker`. Браузерный элемент `img` применяется только для показа выбранного изображения. Его свойства не используются для определения ширины, высоты или других метаданных.

## 2. Интерфейс и организация работы

В верхней области находятся выбор файлов и папки, остановка, счётчики и прогресс. Ниже расположены поиск, фильтры, выбор числа потоков и экспорт. Таблица дополнена карточкой выбранного файла.

На странице выводится не более 100 строк одновременно. Переключение страниц позволяет работать с большой коллекцией без создания 100 000 DOM-элементов. Заголовок таблицы остаётся видимым при прокрутке. Имена и пути вставляются через `textContent`, поэтому содержимое имени не интерпретируется как HTML.

| Поле | Значение |
| --- | --- |
| Имя файла | Имя выбранного файла; полный относительный путь доступен в карточке |
| Формат | Определяется по содержимому, а не по расширению |
| Размер, px | Ширина и высота исходного растра без применения Exif Orientation |
| DPI, X × Y | Число пикселей на дюйм по горизонтали и вертикали |
| Бит/пиксель | Сумма бит каналов, а для палитровых форматов — глубина индекса |
| Сжатие | Способ кодирования пиксельных данных, указанный в структуре файла |
| Статус | «Готово», «Файл поврежден», «Ошибка чтения» или «Не поддерживается» |

Отсутствующее физическое разрешение обозначается «Не задано». Размер изображения в пикселях сам по себе не определяет DPI. Нулевые значения разрешения не заменяются вымышленными 72 или 96 DPI.

Для JPEG, PNG, GIF и BMP используется браузерный предпросмотр. Для TIFF и PCX выводятся метаданные без предпросмотра. Некоторые разновидности BMP браузер может не показать, хотя метаданные будут прочитаны. Автоматический предпросмотр ограничен 40 миллионами пикселей и 100 МБ, чтобы выбор большого файла не приводил к чрезмерному расходу памяти.

## 3. Трёхслойная архитектура

```text
Presentation: index.html, styles.css, view.js, controller.js
                           ↓
Engine: engine.js, worker.js
                           ↓
Infrastructure: model.js → Reader → File.slice()
```

**Presentation** обрабатывает действия пользователя и показывает результаты. Контроллер передаёт список файлов менеджеру, а представление формирует таблицу и карточку. В этом слое нет разбора бинарных заголовков.

**Engine** создаёт пул из 1, 2, 4 или 8 Web Workers, распределяет задания и собирает результаты. Файлы передаются порциями до 16 штук. Один поток последовательно обрабатывает свою порцию и запрашивает следующую. Одновременно работают несколько настоящих рабочих потоков, а не только цепочка Promise в основном потоке.

**Infrastructure** содержит Reader и независимые парсеры. На вход поступает объект файла, на выходе получается объект метаданных или диагностический результат. Обращений к DOM здесь нет. Этот же слой запускается в автоматических проверках без браузерного интерфейса.

Исходный текст парсеров и обработчика Worker собирается в Blob. Благодаря этому рабочие потоки создаются и при открытии через `file://`, без загрузки отдельных worker-скриптов по сети.

Если чтение файлового объекта в Worker недоступно, поток запрашивает диапазоны до 4096 байт у Engine. Основной поток асинхронно читает только запрошенные блоки и передаёт ArrayBuffer обратно; бинарный разбор продолжает выполняться в Worker. Поле выбора сохраняет файловые объекты до следующего выбора. Ошибка доступа обозначается отдельно от повреждения структуры.

При остановке Worker завершается методом `terminate()`. Номер поколения задания защищает от попадания устаревших результатов в новый запуск. Blob URL рабочих потоков освобождается, а кэш Reader очищается после каждого файла.

## 4. Определение формата и чтение по смещениям

Перед выбором парсера проверяются начальные байты:

| Формат | Сигнатура |
| --- | --- |
| JPEG | `FF D8` |
| PNG | `89 50 4E 47 0D 0A 1A 0A` |
| GIF | `GIF87a` или `GIF89a` |
| BMP | `42 4D`, то есть `BM` |
| TIFF | `II` или `MM`, затем число 42 с соответствующим порядком байтов |
| BigTIFF | `II` или `MM`, затем число 43 |
| PCX | `0A`, затем проверка версии, кодирования, глубины и плоскостей |

Если JPEG переименован в PNG, результат остаётся JPEG и появляется предупреждение о расширении. Если под именем `.jpg` находится текст, выводится «Файл поврежден». Обычный текстовый файл с расширением `.txt` получает статус «Не поддерживается».

Reader проверяет границы каждого диапазона до обращения к данным. Чтение выполняется блоками по 4096 байт; одновременно кэшируется не более 16 блоков, то есть около 64 КБ на активный файл. Повторное обращение к тому же блоку не вызывает повторного чтения. В интерфейсе учитывается фактически запрошенный Reader объём, а не размер всего файла.

PNG-парсер переходит от чанка к чанку по их длинам, JPEG-парсер пропускает сегменты по длине, TIFF-парсер переходит по указателям. Пиксельные массивы этих форматов не загружаются для извлечения свойств. Для PCX применяется последовательная проверка RLE: у формата нет обязательного маркера конца изображения или размера сжатого потока, поэтому надёжная проверка обрезания требует просмотра потока серий. Проверка не создаёт распакованный растр.

## 5. Получение данных из каждого формата

### BMP

Из `BITMAPFILEHEADER` читаются размер файла и смещение пикселей. Из DIB-заголовка извлекаются ширина, высота, число плоскостей, глубина, сжатие и физическое разрешение. Поддерживаются заголовки длиной 12, 40, 52, 56, 64, 108 и 124 байта.

Отрицательная высота у Windows BMP означает хранение строк сверху вниз. В таблице выводится абсолютная высота, а порядок строк поясняется отдельно. Для несжатого изображения размер строки выравнивается до четырёх байт:

```text
rowBytes = ceil(width × bitsPerPixel / 32) × 4
pixelBytes = rowBytes × abs(height)
```

Проверяется, что пиксельные данные помещаются в файл. Отдельно учитываются цветовые маски и палитра перед растром.

`BI_RGB` означает отсутствие сжатия; `BI_RLE8` использует серии 8-битных индексов; `BI_RLE4` использует серии двух чередующихся 4-битных индексов. `BI_BITFIELDS` задаёт маски каналов и не является сжатием. Палитра — таблица соответствия индекса реальному цвету. В Windows BMP запись содержит B, G, R и резервный байт; у старого CORE-заголовка используются трёхбайтовые BGR-записи.

Поля X/Y pixels per meter переводятся в DPI умножением на 0,0254. Источник: [BITMAPINFOHEADER, Microsoft](https://learn.microsoft.com/en-us/windows/win32/api/wingdi/ns-wingdi-bitmapinfoheader).

### PNG

После сигнатуры проверяется первый чанк `IHDR`. Из него читаются размеры, глубина одного канала или индекса, тип цвета, метод сжатия, фильтрация и чересстрочность. Тип цвета определяет число каналов: серый — 1, RGB — 3, серый с альфа-каналом — 2, RGBA — 4. Для индексированного PNG глубина относится к индексу палитры.

`PLTE` содержит RGB-тройки; количество цветов равно длине чанка, делённой на три. Из `pHYs` получается физическое разрешение, только если единица равна метру; относительное соотношение осей не объявляется DPI. `IDAT` хранит сжатый поток Deflate. Фильтрация с методом 0 допускает None, Sub, Up, Average и Paeth; метод чересстрочности 1 означает Adam7. Обязательны данные изображения и завершающий `IEND`. Источник: [спецификация PNG, W3C](https://www.w3.org/TR/png/).

### JPEG

Проверяется `SOI` в начале и `EOI` в конце. До начала сжатого скана анализируются сегменты. Ширина, высота, точность компоненты и число компонент читаются из `SOF`. Различаются последовательный, прогрессивный и lossless-режимы.

В `APP0/JFIF` хранятся единицы и X/Y density: для дюймов значение используется напрямую, для сантиметров умножается на 2,54, а единица 0 означает лишь соотношение сторон пикселя. В `APP1/Exif` вложена TIFF-структура. Если она задаёт физическое разрешение, используется Exif; иначе — JFIF.

Дополнительно читается `DQT`. Матрица квантования задаёт делители коэффициентов дискретного косинусного преобразования и влияет на потери при сжатии. Выводятся номер таблицы, точность элемента и 64 значения в том zigzag-порядке, в котором они хранятся в JPEG. Это не процент качества. Источники: [JFIF](https://www.w3.org/Graphics/JPEG/jfif3.pdf), [JPEG T.81](https://www.w3.org/Graphics/JPEG/itu-t81.pdf).

### GIF

Из Logical Screen Descriptor читаются размеры логического экрана и признаки глобальной палитры. При наличии локальных палитр их размер учитывается для каждого кадра. В таблице показывается максимальная глубина индекса использованных палитр. Размер таблицы цветов вычисляется как `2^(N+1)`.

Блоки расширений и сжатые подблоки пропускаются по длинам; кадры считаются по Image Descriptor. Сжатие — LZW. GIF не хранит физический DPI. Поле цветовой разрешающей способности описывает исходную точность компоненты и выводится отдельно от глубины индекса. Число кадров характеризует анимацию, а размеры таблицы относятся к количеству доступных цветов, не к числу реально использованных цветов. Источник: [GIF89a, CompuServe](https://www.w3.org/Graphics/GIF/spec-gif89a.txt).

### TIFF и BigTIFF

TIFF содержит каталоги IFD. Запись тега задаёт идентификатор, тип, число элементов и значение либо смещение к нему. Если данные помещаются в 4 байта классического TIFF или в 8 байт BigTIFF, они находятся прямо в записи. Иначе выполняется переход по смещению относительно начала TIFF.

Реализованы little-endian и big-endian, целые знаковые и беззнаковые типы, RATIONAL/SRATIONAL, FLOAT/DOUBLE и 64-битные LONG8/SLONG8/IFD8. Значения 64-битных смещений проверяются на точную представимость числом JavaScript. RATIONAL вычисляется как числитель, делённый на знаменатель; нулевой знаменатель считается повреждением.

| Теги | Назначение |
| --- | --- |
| 256, 257 | Ширина и высота |
| 258, 277 | Бит на компоненту и число компонент |
| 259 | Сжатие |
| 282, 283, 296 | XResolution, YResolution и единицы разрешения |
| 273, 279 | Смещения и размеры сжатых полос |
| 324, 325 | Смещения и размеры тайлов |
| 320 | ColorMap — три массива компонент палитры |
| 330 | Ссылки на вложенные изображения SubIFD |
| 34665, 34853, 40965 | Вложенные Exif, GPS и Interoperability IFD |

Глубина получается суммированием BitsPerSample. Код Compression переводится в название: без сжатия, CCITT, LZW, JPEG, Deflate, PackBits; неизвестный код показывается явно. ResolutionUnit 2 означает дюйм, 3 — сантиметр, 1 — отсутствие физической единицы.

Проверяются все диапазоны полос и тайлов, цепочка NextIFD и вложенные ссылки. Посещённые смещения записываются в множество для обнаружения циклов. Таблица показывает первое изображение, а карточка — число изображений/SubIFD, число всех каталогов и размеры, глубину, сжатие каждой страницы. Эти числа могут отличаться, поскольку Exif/GPS-каталоги не являются страницами. Источники: [TIFF 6.0](https://www.itu.int/itudoc/itu-t/com16/tiff-fx/docs/tiff6.pdf), [BigTIFF Design](https://libtiff.gitlab.io/libtiff/specification/bigtiff.html).

### PCX

Разбирается 128-байтовый заголовок. Размеры рассчитываются по включительным границам: `width = Xmax − Xmin + 1`, `height = Ymax − Ymin + 1`. Глубина равна числу бит на плоскость, умноженному на количество плоскостей. Поля HDpi/VDpi используются напрямую.

Поле encoding различает несжатые данные и RLE. BytesPerLine задаёт размер строки одной плоскости с выравниванием. Проверяется достаточность строки для ширины изображения. У индексированного 8-битного PCX версии 5 проверяется завершающая 256-цветная палитра с префиксом `0C`.

Для RLE байт с двумя старшими единичными битами задаёт длину серии в младших шести битах; следующий байт — повторяемое значение. При проверке считается количество восстановленных байтов без хранения пикселей. Оно должно совпасть с `BytesPerLine × planes × height`. Источник: [ZSoft PCX Technical Reference](https://www.fileformat.info/format/pcx/spec/a10e75307b3a4cc49c3bbe6db4c41fa2/PCX.TXT).

## 6. Обработка повреждённых файлов

Каждый файл обрабатывается независимо. Исключение перехватывается внутри парсера и возвращается как результат с объяснением. Ошибка одного изображения не прерывает остальные задания.

Проверяются сигнатуры, допустимые параметры заголовков, размеры диапазонов и обязательные структуры. Для PNG контролируются порядок основных чанков, наличие IDAT/IEND и CRC метаданных IHDR, pHYs, PLTE, IEND. Для JPEG — границы сегментов, SOF/SOS и завершающий EOI. Для BMP — размер файла, смещение пикселей, палитра и объём растра. Для GIF — границы блоков, кадры и trailer. Для TIFF — типы, ссылки, дроби и диапазоны полос/тайлов. Для PCX — заголовок, палитра и длина восстановленного RLE-потока.

Проверка структуры не равнозначна полной проверке качества изображения. Содержимое JPEG-скана, TIFF-сжатия, GIF LZW и PNG IDAT не декодируется; CRC больших IDAT не пересчитывается. Повреждение только внутри этих потоков при сохранённых заголовках и длинах может быть обнаружено декодером изображения, но не анализатором метаданных. Это сохраняет возможность быстро читать крупные файлы по смещениям.

Для защиты от чрезмерно сложных структур ограничены число IFD, длины массивов и количество операций чтения. Достижение предела показывается как ошибка с конкретной причиной.

## 7. Производительность и многопоточность

Параллелизм ограничен выбранным размером пула. Программа не создаёт по Worker на каждый файл и не запускает 100 000 одновременных чтений. Новая порция выдаётся освободившемуся потоку. В память передаются файловые объекты и небольшие результаты, а не полные массивы содержимого.

Список File-объектов и результаты занимают O(N) памяти. Кэш чтения ограничен O(W × 64 КБ), где W — число потоков. На странице размещается до 100 строк. Перерисовка таблицы объединяется с интервалом около 350 мс; завершение и действия пользователя отображаются сразу.

Обход вложенных каталогов при перетаскивании асинхронен; чтение метаданных выполняется в пуле Worker. При выборе через диалог список файлов предоставляет браузер. Поиск и сортировка массива результатов остаются в основном потоке, поэтому на очень слабом устройстве обработка 100 000 строк может давать короткие задержки. Сам бинарный разбор выполняется вне UI-потока.

## 8. Автоматическая проверка

Проверяются все шесть форматов, разные глубины цвета, палитры, progressive JPEG, несколько способов сжатия TIFF, многостраничность, Exif, оба порядка байтов TIFF, BigTIFF, полосы и тайлы, дробные DPI, отсутствие физических единиц, циклы и ошибочные смещения. Отдельно проверяются обрезанные файлы, неверные сигнатуры, CRC, огромные длины чанков, отсутствие IEND и подменённое расширение.

Тестовые изображения в `fixtures` подготовлены отдельно. Библиотека Pillow использовалась только при подготовке и независимой сверке тестовых данных; она не входит в приложение, не вызывается при работе пользователя и не нужна для запуска тестов. Синтетические TIFF/BigTIFF и повреждённые заголовки дополнительно формируются самим тестом.

В предоставленном наборе 24 BMP-файла: все прочитаны успешно, глубина каждого — 8 бит, сжатие — BI_RGB, физическое разрешение отсутствует. На каждый файл требуется 4096 байт чтения. Набор вместе с ними содержит 175 проверок, без внешней папки — 151. Полный результат находится в `test-results.json`.

### Нагрузочные и браузерные проверки

Проверка выполнена в Yandex Browser 26.8 на macOS, с четырьмя рабочими потоками. Измерено время анализа после получения списка файлов, без времени работы диалога выбора.

| Набор | Результат |
| --- | --- |
| 600 JPEG на диске, 1 960 734 000 байт | 600 успешных результатов, 0,11 с; прочитано 4,28 МиБ |

Этот замер отражает работу с доступным файловым кэшем и чтение метаданных, а не скорость полного чтения 2 ГБ с холодного накопителя.
